# TLA+ models of byoa's concurrent protocols

These models check the parts of byoa where several backends, sandboxes, clocks and the app's own calls act on one user's state at the same time. TLC, the TLA+ model checker, tries every order of their steps in small worlds (two or three jobs or backends), with backends that die, leases that run out, clocks that differ, and stores that answer late or twice. This is check V22 in [SPEC.md](../../SPEC.md#verification).

```sh
TLA_SET=ci spec/tla/check.sh   # the fast set, which CI runs: about 15 minutes on 1 core, less with more
spec/tla/check.sh              # every model: several hours; some of the 3-job models need 4 GB or more (TLC_HEAP=4g)
spec/tla/check.sh SignIn       # the models whose file names contain "SignIn"
```

`check.sh` needs Java 11 or later. It downloads `tla2tools.jar` 1.7.4 the first time, and checks its SHA-256. Each model in `models/` is `<Spec>_<name>.cfg`, and its first three lines say:

1. what TLC must find: `\* expect: ok` (no error), or `\* expect: violated <Property>` (a counterexample that TLC must still find: an open issue, a known limit, or the code before a fix, kept so the fix stays needed);
2. why, in one sentence;
3. its set: `\* set: ci` (small; `.github/workflows/tla.yml` runs these on each push and pull request that changes a model or the code it models) or `\* set: full` (bigger bounds: three jobs or backends, longer times; the workflow runs every model when it is started by hand).

Names: `main_*` is the code before a fix found here, `fixed_*` the code with it (or with a fix that is only proposed, when its line 2 says so), `heartbeat_*` the code before the first pass's second fix, `live*` a liveness check. A spec's header says what it models, with the file, function and line numbers of each step at d7c34b7, its fairness, and every place where it differs from the code.

**Fairness.** Every liveness model states it in its spec (`Fairness`, `FairSpec` or `LiveSpec`): weak fairness on each step of a live backend (a store or sandbox call ends; a poll loop that sleeps runs again), on time, on the provider's timers and the watcher's `sleep`, and on the cron; strong fairness where a step can be disabled again and again (Postgres's lock queue, a replica that catches up). A dead backend, the app's own calls, and the user get none. No liveness model uses SYMMETRY, since TLC's liveness check is unsound with it.

## What TLC found

The second pass (this branch) found these; each one fixed here has a test that fails on d7c34b7.

**Fixed here**

1. **A sign-in that `signOut` or `cancelLogin` overlaps** (the first pass's open item; `SignIn_main_signout`, `_main_volume`, `_main_cancel`, `_main_twostarts`). `finishLogin` deleted the sign-in's entry, then saved the login and set `signed-in`: a `signOut` in between returned, and the user was then signed in again. A `cancelLogin` while `connectLogin` created its sandbox found no entry, so the sandbox lived 2 more minutes; two `connectLogin` at once left the first sandbox with no entry that named it. Now the entry is written before the sandbox, ended with compare-and-set and never deleted; `connectLogin` registers its sandbox, and `finishLogin` saves the login and the state, only while the entry is still its own; and with `storedLogin`, the state is `signed-out` whenever no login is stored (`SignIn_fixed_*`). A review of that fix found that a `cancelLogin` between `finishLogin`'s check and its save still let the login stay (`SignIn_main_cancelwins`, `_main_cancel_in`): `finishLogin` now puts the earlier login back while the key still holds what it wrote. A sign-in sandbox whose destroy failed was dropped from the entry (`SignIn_main_keep`); the entry now keeps it. Tests: "R1.7: a cancelLogin while connectLogin creates its sandbox ends that sandbox", "R1.7: two connectLogin at once …", "R1.6: a signOut while finishLogin saves the login wins (storedLogin)" and "(cliLogin)", "R1.7: a cancelLogin while finishLogin saves the login wins: no login stays", "R1.7: a sign-in sandbox that finishLogin could not destroy stays known …".
2. **A job that waits long for the AI login loses the kept sandbox** (`JobTiming_main_wait`, `_main_wait_idle`). The sandbox's time was set at resume and again only once the job had the login; a wait longer than the job timeout + 60 s let E2B pause the sandbox, `load` failed, and `close` destroyed the user's kept sandbox and its job folder. With `sandboxPer: 'job'`, E2B ended the sandbox. Now resume, create, and the beat that renews the slot's lease every minute until the harness starts, give the sandbox 1 minute more than the job timeout + 60 s, so the watcher always runs first (a review found that without it on resume and create, a `load` before the first beat still left a gap: `JobTiming_main_firstbeat`). Daytona's kept sandbox has no `setTimeout` and stops when idle: that case stays open (below). Test: "a job that waits in line for the AI login longer than its sandbox's time keeps its sandbox".
3. **The login left in a paused sandbox by a backend that died during `load`** (`JobTiming_main_settime`, `_main_load`). The watcher's time was later than the sandbox's own time until `setTimeout`, and `load` wrote the login files before it started the watcher. Fixed by the beat (2), and `load` now starts the watcher first. Tests: "the login's watcher runs before the provider would pause the sandbox …" (two), "a backend that dies while load writes the login …".
4. **The job ended before the turn that answers a message the app sent** (`Steer_main_*`, all three CLIs). The reader reads the driver's output ahead of the app, so when the job handled a turn's end, `reader.taken` could already count the message the next turn took; the job then ended with the earlier turn's answer. Now each end event carries the count at the time the reader read it. Tests: "R5.10: a claude/codex/grok job whose app reads its events slowly still answers the message it sent before it ends".
5. **A failed Grok turn whose prompt is answered late failed the next turn** (`Steer_main_grok_fail`): the driver took that late error for a turn that did not start, and ended Grok. Now it counts `turn_completed`. Test: "R5.10: a grok job goes on with the next message after a failed turn …".
6. **A slow token endpoint, or a 5xx, made the user connect an MCP server again** (`Grants_main_slow*`, `_main_transient`). A refresh longer than the 30 s lease let a second backend refresh with the same, now revoked, refresh token, mark the grant `needsSignIn`, and lose the first refresh's new tokens; and `auth()` ends in `REDIRECT` also after a 5xx or no answer, which byoa took for a refused token. Now the refresh renews its lease every 10 s while `auth()` runs and releases it by id, so a slow token endpoint gets one request (`Grants_fixed_*`; `Grants_norenew_*` is the first fix without it, which a review showed still told requests to connect again, and lost the grant with a server that revokes the token family on reuse). byoa reads the token endpoint's answer: only a 4xx that is not "try again later" marks the grant (any OAuth error, or a body that is none); a 5xx, 408, 429 or no answer fails that request only. A refresh whose save loses to a mark writes its tokens over it. Tests: "R2.3: a refresh slower than its lease (30 s) renews it …", "R2: a token endpoint that refuses the refresh token in any way …", "… when a second refresh still comes (a backend clock more than 20 s ahead) …".
7. **A retry after a 401 got the refused token again** (`Grants_main_stale`), when this process's refresh of that token was still settling. Test: "R2.3: a 401 for the token that this process's refresh is just giving out refreshes again". It joins one more refresh, no more, so a server that answers with the same token is not called in a loop.
8. **`removeMcp` while the user connected the same server again left a grant no index listed** (`Grants_main_index`): `listMcp`, the proxy and `fetchWithGrant` did not see it, and an app that deletes a user through `listMcp` never deleted it. `save` and `remove` now do what Index.tla's fix does. Test: "R2: removeMcp while the user connects the same server again keeps the grant listed".
9. **A lost answer from the store left a slot lease that no job used** (`Store_lease_main_lostack`, `_main_retry`). A `cas` that committed but threw (a network error after Postgres's commit), or that an app's retry wrapper sent again (the second send answers false), made `take` fail or wait behind its own lease for the job timeout + 5 minutes. Now `take` holds a lease that names its own holder, also on a later poll when the read after the cas failed (`Store_lease_main_getfail`), and gives back a lease it may have written when it does not get the slot (`Store_lease_poll_wait` shows why). A review also found that the job's own beat, between `slots.set`'s read and write, failed the job and stranded the slot (`Store_lease_main_beat`): `set` and `renew` now try again while the holder holds the slot. The login lease's `take` had the same lost-answer problem and has the same fix (a test only; not modeled). Tests in `test/store.test.ts` and "R1.4 / R6: a lease of the login that the store wrote but whose answer was lost is the job's".
10. **A job token ran out while its harness ran** (`Tokens_main_wait`): its time started when the job began, before the wait in line, so a job that waited lost its MCP servers (and, with a plan, its relay). The job now extends its token with compare-and-set when its harness starts. Test: "R3.1 / R3.4: a job that waits in line keeps its job token for its whole time".
11. **A job that worked cleared a usage-limit hold another job kept while it ran** (`UsageLimit_main_clear`), and **a job that kept an earlier reset ended a later one too soon** (`UsageLimit_main_stale`): the next jobs each started a sandbox on a used-up plan. `clear` now ends only the hold the job read (compare-and-set to an empty value), and `set` keeps the later reset. Tests: "R1.9: a job that worked ends only the hold it read …", "R1.9: a used-up plan holds until its latest reset …".
12. **The mail demo** (`Demo_main_*`; `examples/mail/convex`). The sweep could start the queued job of a visitor it was forgetting, and a forget or Delete my data deleted the rows of a visitor who came back meanwhile: in both, a sandbox stayed that nothing deletes, against the demo's promise. Delete my data skipped `signOut` when the state still said `signed-out` while a sign-in saved its login, so the login stayed. A job that waited over an hour let the visitor start a second one, and a sign-in again took a place with none free. Now the sweep fails the queued job of a visitor it forgets and waits while their job runs, `drop` deletes nothing when the visitor started a job or a sign-in since the forget began (a count of those requests, not the page's 5-minute touch, which made Delete my data fail for nothing: `Demo_main_touch`; Delete my data then asks to try again), and also deletes the visitor's byoa rows that hold no login, the forget always calls `signOut`, `startJob` looks at the last job of any age, and a sign-in again counts the places after the old one ends. Tests in `examples/mail/demo.test.ts`.

**Open**

- **A hold or a login state of the old credential written after the new one** (todo tests in `test/login.test.ts` and `test/plan.test.ts`). A job that ran on the old login or key can keep a usage limit after a new sign-in or `connectKey` cleared it (`UsageLimit_signin`, `_newkey`), so the user is refused, up to a week, with a plan that works; a job of the new sign-in can have its hold cleared by that sign-in (`UsageLimit_signin_lost`). An old key's 401 can mark a new key `expired` (`PlanKey_main_newkey`), and a job that worked before another job's 401 can set `signed-in` over `expired` (`PlanKey_main_report`). Proposed: tag each limit and each state with the credential it is about (the key's store version, a sign-in counter), and ignore one of another credential (`PlanKey_fixed` checks the state part). A request that the proxy checked just before a job's end is still served after it (`Tokens_inflight`, `PlanKey_inflight`), which R3.4 allows; a dead backend's token record stays in the store until a request after its time (`Tokens_crash`).
- **A backend clock more than 20 s ahead** still sees a renewed grant lease run out, and two refreshes can then go out (`Grants_fixed_skew_large`; the stored grant keeps the first one's tokens). A time limit on `auth()` instead of the renewal would be worse: an aborted request can still rotate the token (`Grants_proposal_timelimit`).
- **`removeMcp` deletes a lease that a refresh of the reconnected grant holds** (`Grants_main_remove_lease`, still with the fixes: `Grants_fixed_remove_lease`; a todo test in `test/mcp.test.ts`): a second backend then refreshes the same token. Proposed: `remove` keeps the lease record. **A removed grant can be listed again** for a moment (`Grants_index_ghost`).
- **A failed inbox write leaves a steered job waiting until its timeout** (`Steer_writefail`, `_writefail_inbox`): `write()` hides the error, `send` says true, and the driver never reads past that message. Proposed: retry the write, then end the job with a `sandbox` error and make `send` false; put the task first before the inbox exists. Two assumptions about the CLIs also matter: a Codex that acks a steer and drops it (`Steer_codex_drop`), and a Grok that sends its interjection notice when it queues the message (`Steer_grok_queue`), each end the job early or late.
- **A job that takes the login during `signOut`** runs on after `signOut` returned (`SignIn_main_job`; proposed: `deleteSandbox` again after the login is gone, `SignIn_fixed_job`). A job that ran on the old login can afterwards write a usage limit (`SignIn_limit`), `expired` (`SignIn_report_expired`) or `signed-out` (`SignIn_report_out`) over the new sign-in's state; with `cliLogin`, a sign-in that starts during `signOut` can leave `signed-in` with an empty volume (`SignIn_volume_state`) until the next job finds no login.
- **Daytona: a long wait for the login stops the kept sandbox** (`JobTiming_main_wait_idle`): it stops when idle and has no `setTimeout` for a kept sandbox. Proposed: the beat calls Daytona's `refreshActivity()` (`JobTiming_fixed_idle`). Instabox likely has the same issue (it suspends after 30 min idle); not modeled. `listModels` waits for the login with no renewal of its 10-minute sandbox.
- **Stores that are not linearizable** (`Store_index_main_stale`, `_line_main_stale`, `_line_stale_leave`, `_lease_aba`): with a read replica or a cache in front of `get`, an index can lose an entry and the line can serve a later job first; with versions that repeat after a delete, a job can take a running lease. No adapter in this repository does either; `src/store.ts` and `docs/stores.md` now say what an adapter must give.
- **The demo's sign-out sandbox** (`Demo_main_cap`): byoa's `signOut` starts a sandbox for the CLI's logout, which the demo does not count; it needs a place of its own (waiting for a job's place starves the forget, `Demo_proposal_cap_starve`). With the sign-in fix, a Delete my data while a sign-in saves leaves no login (`Demo_fixed_delete`); a sign-in that starts during Delete my data can keep its sandbox, with no login, up to 2 minutes after it.
- **The help agent** (proposals for madeyexz/byoa-help, not applied): its sweep fails a job at 6 minutes while the action may run 10, so a third sandbox can start (`Help_main_cap`; `STALE_JOB_MS` of 11 minutes fixes it), a forget can race a question that starts, or a visitor who asks while it runs (`Help_main_forget`, `Help_main_return`; the proposal adds the demo's checks, `Help_fixed_forget`), and a question that waited over an hour lets the visitor ask a second (`Help_main_onejob`). Its one login is never refreshed by two CLIs at once (`Help_refresh`).

**Found by the first pass, fixed then:** the slot lease that ran out while a job waited for the login (`JobTiming_main_slot`), the watcher and sandbox time that started before that wait (`JobTiming_heartbeat_*`), and index orphans in `deleteConversation`, `deleteSandbox` and `signOut` (`Index_*_main`, `Index_conversation_crash`).

**Known limits, as SPEC.md says.** A dead backend loses a refresh its CLI made after the last checkpoint (`JobTiming_fixed_crash_loses`, `LoginLease_crash_lost`). A CLI that refreshes early after a 401 (`LoginLease_early401`), or a backend clock more than the lease's margin ahead (`LoginLease_skew_large`, `Grants_skew_large`), can make two refreshes. A backend that dies in its write while a remove runs can leave one index entry (`Index_*_fixed_crash`, `Grants_fixed_index_crash`). A backend that dies between `finishLogin`'s resume and its `keepAlive` leaves the sign-in sandbox up to 2 minutes + `waitMs` past its 15 minutes (`SignIn_cap_crash`).

**Holds**, in every model with no error: one job alone holds a login that is due, and a shared login is never refreshed by two CLIs; no save puts an older login or another account's over the stored one; the line serves jobs in order and every waiting job gets its turn while backends live; one job runs in a kept sandbox at a time; with the fixes, the login never stays in a paused sandbox; a sign-in that the app left ends; every message `send` accepted is answered before the job ends (when the writes work); no removed grant is put back by a refresh; each adapter in this repository is linearizable with versions that never repeat; and in the demo, nothing of a visitor stays past the hour.

## Store adapters

| Adapter | Linearizable | Stale reads | Lost answer | Retries | Versions repeat |
|---|---|---|---|---|---|
| `memoryStore` | yes: no await inside a call, one JS thread | no | no | no | no: one counter |
| `sqliteStore` (examples) | yes: one autocommit statement; SQLite's lock serializes processes on one file | no | no: in process | no | no: a random UUID per write |
| `postgresStore` on the primary | yes: autocommit statements; READ COMMITTED re-checks an UPDATE's WHERE on the latest row, and ON CONFLICT inserts or updates | only if the app's `query` sends a select to a replica | **yes**, rarely: a network error after the commit | only if the app wraps `query` with a retry | no: one sequence |
| `convexStore` | yes: each mutation is a serializable transaction | no (byoa does not use `useStaleSnapshot`) | not documented | a mutation from an action is retried only on a conflict, before it commits | no: `<_id>.<n>` |

## Where the models differ from the code

Each spec's header lists its own simplifications, and names the code lines of each step. In short:

- Small worlds: two or three jobs or backends, one user, one key, and short times. The models keep the order of the code's times (the 60 s and 45 s margins, the 5-minute lease margin, the 30 s grant lease and ticket, the demo's hour and its stale-job time) and scale them down.
- A step of a live backend takes less than one step of time. A real backend can stall longer, as when an event loop blocks; that is like a clock that is behind.
- Several awaits of one call are one step where no other process can see the difference; each header argues it.
- The CLIs' own behavior (when they refresh, that they rotate refresh tokens, how each takes a message during a turn) is a nondeterministic choice among what its protocol allows, from the comments in `harness/*.ts` and the stand-ins in `test/fixtures/bin`.
- Apart from Store.tla, the store is linearizable and its versions never repeat for a key, which holds for every adapter in this repository (the table above).

**Not modeled:** the login lease under a lost store answer (a test checks the fix); Instabox's idle suspend; E2B Hobby's 1-hour limit; a CLI that crashes; client re-registration (`invalid_client`); a user who revokes an MCP grant at the server; several keys of one store at once; Convex giving up after many conflicts.

Apalache was not used: the specs would need type annotations and a rewrite around their optional records, and the bounded models gave the results in the time there was. The inductive invariant to try for `NoRefreshRace` with an unbounded clock (and no skew): a lease held alone and shared leases are never both live; every sharer read a login due after its lease ends, and its CLI ends before that lease's end minus the margin, so no sharer refreshes; the version that `take` checked is the stored one; and a dead holder's lease outlives its CLI. A refinement of JobTiming to a mutex would add little: `OneJobPerSandbox` checks just that.
